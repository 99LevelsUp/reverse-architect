# reverse-architect

**Point it at a source tree and get back a linked set of Markdown cards that explain the code:** a map of every module, a short card per type, file and module, a detail behind each card that has more to say, and pages for the architecture, hot spots, inheritance and integrations. Every statement names the file and line it came from, so a message from a log or the name of a table leads to the member and the line in one search.

reverse-architect is deterministic, offline and needs no LLM. It parses the code, builds one fact graph of declarations, calls, references, imports, inheritance and tests, and projects that graph into documents a person or a retrieval pipeline can read. The same commit always produces the same bytes.

Languages come as sandboxed WebAssembly plugins. The standard build ships **C#, TypeScript/TSX, JavaScript, Python, Rust, Go, Java, SQL and XAML**, and anyone can add another without touching the core. **C and C++** have no plugin: the host reads their string literals, comments and SQL, but not their declarations (see [C and C++](#c-and-c)).

## What you get

```
myproject.reverse-architect/
├── index.md              start here: modules, notable types, where to read next
├── overview.md           size, languages, entry points
├── architecture.md       module map, dependency layers, cycles, extension points
├── hotspots.md           the most-used and most-coupled code
├── hierarchy.md          inheritance and implementation trees
├── integrations.md       what the code talks to outside itself
├── dependencies.md       declared package dependencies
├── entry-points.md, module-structure.md, test-coverage.md
├── cards/
│   ├── map/…             one map per module: a row for each of its types
│   ├── module/…          one card per directory
│   ├── type/…            one short card per class, interface, struct, table, …
│   ├── file/…            one card per file
│   └── detail/
│       ├── type/…        what a type's card leaves out: texts, database, API, every relation
│       └── file/…        texts and database accesses no type of the file owns
├── coverage.json         what was analyzed, and why anything was not
└── manifest*.json(l)     the graph and every document, chunked for RAG
```

````markdown
## Purpose

Restores a backup into the current database. (from the comment)
Implements `ILoadAction`; writes `dba.ops_schedule_tasks`; reads `dba.ops_backup_history`; calls `dba.ops_refresh_tasks`. (from the structure)

## Keywords

ops, tasks, dba, schedule, refresh, ops_schedule_tasks, history, invalid, ops_backup_history, ops_refresh_tasks, current, database
````

````markdown

- `Zálohu se nepodařilo obnovit do aktuální databáze` → `Fail()` · `Actions/Backup/LoadAction.cs:39`

## Database

- `RefreshTasks()`
  - reads `dba.ops_backup_history` — `Actions/Backup/LoadAction.cs:34`
  - calls `dba.ops_refresh_tasks` — `Actions/Backup/LoadAction.cs:33`
- `SetScheduledTasksInvalid()`
  - writes `dba.ops_schedule_tasks` — `Actions/Backup/LoadAction.cs:24, 26`
````

Cards say what the code does in sentences, not just what it declares. Each card links to the cards it depends on and to the cards that use it, so the corpus reads like a wiki. The detail lists every relation with how far it can be trusted. A solid line in a diagram is a relation an index or a rule backs. A dotted line is a name match nothing backed. A relation the tool could not settle is neither drawn nor listed with the others: it goes to a separate "Maybe also" section of the detail with the reason, and is never presented as fact. [How far a relation can be trusted](#how-far-a-relation-can-be-trusted) explains the levels.

## Three levels: map, card, detail

Navigation starts at the module, not at a full-text search. Each level links to the next one down.

| Level | Where | What it holds |
|---|---|---|
| Map | `cards/map/<module>.md` | One row per type of the module: its kind, a link to its card, its purpose in brief and what sets it apart — the database objects it `writes`, `reads` or `calls`, what it implements or extends, whether it is an entry point. Types that generators and designers produce (by file name or an `<auto-generated>` header) share one row with their count. A map of more than 50 rows (the merged row of generated types counts as one) is cut into `## Part N` sections of at most 50 rows; no hand-written type is left out. The module card links its map. |
| Card | `cards/type/…`, `cards/file/…`, `cards/module/…` | A type's short card: a one-line header read from the signature (a `public static class` says so) that names the module by its last segment, a link to the detail, `## Purpose`, `## Role` with the main relations grouped into sentences and a count of the further neighbours the detail lists (and how many of those are uncertain), and `## Keywords`. A neighbour is *uncertain* when it is reached only through name matches the resolver rules did not settle; the detail names each under "Maybe also" with the reason. No signature, no test pairing, no API list, no diagram, no full relation lists. |
| Detail | `cards/detail/type/…`, `cards/detail/file/…` | Everything the card leaves out: the quoted comment, `## Signature`, `## Anchors`, `## Database`, `## Enum decisions`, the API, every relation with its confidence level, "Maybe also", the diagram, `## Test pairing` and the notes. A detail is written only when it says something its card does not; the signature and the test pairing alone do not earn one, so a type without a detail shows its kind and modifiers in the card's header line only. One larger than 8 KiB is cut into `## Part N` sections, with its sections as `###` inside each part. |

A person or an agent finds the code for a message, a method or a table in one of two ways: search the corpus for the text and land on the line of a detail that names the member and the source line, or open the module's map and follow the row to the card and the detail.

### Purpose

A type's purpose is put together from its structure and its comment, never guessed. Each sentence ends with where it comes from: `(from the comment)` is the first sentence of the doc comment, and `(from the structure)` is what the code shows — a stereotype from the base types and interfaces, the shape of the members (only data, only static methods, a factory), whether it is an entry point, and the database objects and external resources it reaches. A type with neither comment nor recognized structure gets only the facts the structure states. The map row and the manifest header carry the same purpose in brief.

### Keywords

Every card carries at most 12 keywords from four sources: the identifiers split at case changes, underscores and digits, the names of database objects, the words of string literals and the words of comments. Words typical of the type within the corpus come first (an integer score from how often the word occurs in the type and how rare it is across all types, ties broken in code-point order). A word with diacritics is followed by its spelling without them, so `zálohy` is also found as `zalohy`.

### Anchors

A detail's `## Anchors` section lists the texts a reader may search for — string literals and comment lines — each with the member it sits in and the line. The host's lexer reads them for every language, so a plugin does not report them. Identical texts in one member are one anchor with the first line; a member keeps at most 48 of them (texts of several words first), and each is cut at 160 characters. A text the secret filter withheld leaves only its place and the reason (`withheld: password`), never its value. Doc comments are not anchors: the detail quotes them under `## Documentation`.

### Database accesses

`## Database` lists, per member, the database objects its SQL names, each with the lines: `reads`, `writes`, `calls` (a procedure, `exec dba.proc`) or `mentions`. The state is read per SQL statement: the target of an `UPDATE`, `DELETE`, `INSERT` or `MERGE` is written even where the statement names it again in its own `FROM`, other objects after `FROM` or `JOIN` are read, and `exec` calls. Where the statement's target cannot be told, the object is only `mentions`, and the detail claims nothing more. SQL is read from ordinary, verbatim, raw (`"""…"""`) and interpolated C# literals and from the literals of every other language. A table has no card of its own; it is named by the same stable name everywhere, so a tool that maps the database can link to it.

### Enum decisions

The detail of an enum lists where the code decides by its values, with the lines: `case X.Y` labels, switch-expression arms `X.Y =>` and comparisons (`==`, `!=`, `is`). A label or an arm is verified only when `X` can name this enum alone among the types visible from that file (nested types, its namespace and the parent namespaces, `using` directives and aliases). Comparisons are always listed apart as unverified, because without a syntax tree a local variable of the same name cannot be ruled out. C# is the first language with enum decisions; `coverage.json` counts the places it could not match.

### C and C++

`.c`, `.h`, `.cpp`, `.cc`, `.cxx`, `.hpp`, `.hh` and `.hxx` files have no plugin. The host lexer reads their literals, comments and SQL, so they get anchors, keywords and database accesses, but no types or members. Their texts belong to the file: the file card links a file detail with `## Anchors` and `## Database`. `coverage.json` names them as a language with the reason that no plugin reads their declarations.

### What to import into a knowledge base

Import the maps and the cards. Leave the details out. A knowledge base that embeds every document it imports would let the long lists of the details crowd out the cards in its vector index, and a message is found there through the keywords of the card. The details are for an agent or a pipeline that reads the files: it follows the card's link or searches the text of the details directly.

The manifest says this per document, so an importer does not have to guess from paths. Every map, card and detail is a document with a `level` (`map`, `card` or `detail`), and a detail carries `embed: false`. A document's `id` is stable from run to run (`map:<module>`, `detail:<card identity>`, the card's identity), so it serves as the `source_ref` of the imported document. `parent` names the document one level up, and `header` holds the full context of the entity: the source `path`, the `module`, the `namespace`, the `kind` as the signature states it, the `name` and the `purpose`. When upgrading from cards of format 5, replace every imported document: the cards changed shape and the details and maps are new documents.

## Install

reverse-architect is a single Rust binary. The language plugins are compiled into it.

```sh
cargo install --git https://github.com/99LevelsUp/reverse-architect
```

The repository pins its toolchain in `rust-toolchain.toml`, and rustup installs it on first build.

## Use

```sh
reverse-architect path/to/project                 # writes path/to/project.reverse-architect/
reverse-architect path/to/project --out docs/arch # choose the output directory
reverse-architect path/to/project --lang cs       # card prose in Czech
reverse-architect path/to/project --links obsidian
```

| Option | What it does |
|---|---|
| `--out DIR` | Output directory. By default a sidecar `<name>.reverse-architect/` is written beside the project. |
| `--lang en\|cs` | Language of the explaining sentences. Headings and the fact vocabulary stay English. |
| `--links portable\|obsidian` | Relative Markdown links, or `[[wikilinks]]` for an Obsidian vault. |
| `--plugin PATH[=sha256:HEX]` | Load a language plugin. Repeatable. See [Plugins](#plugins). |
| `--scip-index FILE` | Read a [SCIP](https://github.com/sourcegraph/scip) index, one the project's CI produced or one [`reverse-architect index`](#optional-build-a-scip-index-for-c) built. A relation the index confirms is marked as resolved by the index, and a name match it contradicts moves to "Maybe also". Generation only reads the index. It never runs a build or an indexer. |
| `--secret-prefix PREFIX` | An extra token prefix to treat as a credential. Repeatable. |
| `--ambiguity-ceiling N` | Maximum number of candidates a name match may still turn into edges (default 8). |
| `--mirror` | Also write a copy into `.reverse-architect/` inside the project. |
| `--sites` | Also write `sites.jsonl` beside the manifest: every place a name was used, the declarations it could mean and what each rule said about each of them. Off by default, because the corpus states relations, not call sites. |
| `--model-verification` | Read the layer [`verify`](#optional-let-a-model-check-the-ambiguous-sites) wrote and mark the "Maybe also" lines it answered. Off by default. |
| `--model-purpose` | Read the layer [`verify --purpose`](#optional-let-a-model-say-what-a-type-is-for) wrote and show the model's sentence as a labelled line under a type card's purpose. Off by default. |
| `--detail-level 1\|2\|3` | Also read the bodies of the members and render a second layer on the C# type cards: what the type does, through which entry points, under which preconditions and in which steps, and the states it keeps. A higher level shows more of it. A file whose bodies could not be read gets a `body_extraction_failed` fact and a line in `coverage.json`. Off by default. Without it the body component is not even loaded. |

The input is preferably a git repository. The tool then reads the committed index, so uncommitted edits do not leak into the output. A plain directory works too.

A second run over an unchanged tree is served from a cache in the output directory. The cache is invalidated by any change to the files, the options or the plugin set.

### How far a relation can be trusted

A call, a construction or a type reference found by name can mean more than one declaration. The host resolves every name the same way for every language. It collects the declarations of that name in the repository as candidates, and a fixed catalog of rules sifts them using what the plugin read around the usage: the receiver, its declared type, the argument count, the visible namespaces and where a nested type's simple name reaches. Each rule backs a candidate, disputes it, or says nothing. Every such relation then carries one of four confidence levels, and the card, the detail, the diagram and the manifest all read the same value:

| Level (`confidence` in the manifest) | Meaning | In the detail |
|---|---|---|
| `resolved_by_index` | A SCIP index (`--scip-index`) says this is the declaration. | Main lists. |
| `rules_backed` | The only candidate at that place that a rule backed and no rule disputed. | Main lists. |
| `name_only` | The only declaration of that name in the repository, which no rule backed or disputed. The real target may still lie outside the repository. | Main lists, labelled `name only`. The diagram draws it dotted. |
| `ambiguous` | A rule disputed this candidate, or several are left and no rule picked one. | Not in the main lists. Under `## Maybe also`, one line per place in the source, with the reason (the rule that disputed it, the index pointing elsewhere, or a name several declarations share) and `1 of N candidates` when there are several. |

The manifest also names the rule that decided (`rule_id`) and the places each relation was read at (`sites`). Nothing is silently dropped. A rule may remove a candidate outright only after a measurement against an index has shown that it never removed one the index confirmed (see [measure](#optional-measure-the-resolution-rules-against-the-index)). This build grants one such right: `role-mismatch` for C# (a construction or type position never leads to a method), measured on a large C# ERP code base where it removed nothing the index confirmed (`docs/measurements/2026-10-09-csharp-reference.json`). Every other rule only moves a candidate to "Maybe also".

A call on a built-in type spelled as its keyword (`string.IsNullOrEmpty(x)` in C#) never becomes a relation into the repository.

C# is the first language whose plugin reports the context the rules need. The other bundled languages report names without it, so their calls, constructions and type references stay `name_only` or `ambiguous`. Inheritance is rated the same way for every language: a base found by its spelling (in the type's own module, or by the qualified path the source writes) is `rules_backed`, and one found only as the one type of that name anywhere in the repository is `name_only`.

### Optional: an LLM narrative on top

`reverse-architect enrich <repo> --backend ollama|openai-compat|claude-cli` adds an interpretation around the verified facts. A guardrail checks every generated claim against the graph and falls back to the deterministic text when a claim does not hold. The core output never depends on it.

### Optional: build a SCIP index for C#

`reverse-architect index <repo>` builds the index that `--scip-index` reads. It needs the .NET SDK and [scip-dotnet](https://github.com/sourcegraph/scip-dotnet) (`dotnet tool install --global scip-dotnet`). It indexes every tracked `.csproj` separately with a time limit (`--timeout`, seconds per project) and merges the results into one `index.scip`. By default the file goes into the sidecar directory (`--out` chooses another). A record `index.record.json` lies next to it with the index's SHA-256, the commit, whether the working tree was dirty, the tool versions and the outcome of each project, and `index.logs/` holds each project's output.

> **Warning:** this step runs the repository's build logic (MSBuild targets, props and analyzers) on your machine. Do not run it on a repository you do not trust. It is the only step of reverse-architect that executes the repository's own build logic. Generation never builds and never runs an indexer.

`dotnet restore` is off by default, because it reaches the network and runs package build logic of its own. Without it, a project whose packages were never restored is indexed without them. With `--restore`, each project is restored by its path (`dotnet restore <project>.csproj /p:EnableWindowsTargeting=true`) right before it is indexed, under the same time limit and into the same log, and a project whose restore fails counts as failed. scip-dotnet's own restore is always turned off: it restores the working directory without naming the project, which MSBuild refuses in a directory holding two project files, and scip-dotnet would then index the project without its packages while reporting success.

If a project fails, nothing is written and the exit code is non-zero. `--allow-partial` keeps an index of the other projects, and the record marks it as partial.

```sh
reverse-architect index path/to/project --restore
reverse-architect path/to/project --scip-index path/to/project.reverse-architect/index.scip
```

### Optional: measure the resolution rules against the index

`reverse-architect measure <repo> --scip-index <file>` counts, for each rule that sifts name candidates, how often the index confirmed what the rule backed and whether the rule ever disputed a candidate the index confirmed. It proposes a right to delete for the rules that never did. The report holds counts only, no file or symbol names. The step refuses an index without the record from `index`, one whose SHA-256 does not match that record, one built at another commit or from a dirty working tree, and a partial one. A proposal changes nothing by itself. A right is granted by committing the report and a record in code, as [docs/measurements/README.md](docs/measurements/README.md) describes.

### Optional: let a model check the ambiguous sites

Where there is no index, `reverse-architect verify <repo> --backend ollama|openai-compat|claude-cli` asks a model which candidate each ambiguous usage site means. The model sees the code around the site (12 lines above, 6 below, at most 4 kB) and the candidates, and answers with one of them or with none. Any other answer leaves the site unverified. The snippet and every other part of the question pass through the secret filter, with your `--secret-prefix` values, before they are sent. A cloud backend still receives your source code, so `--dry-run` first prints how many sites would be sent and roughly how many tokens that is. `ollama` keeps everything on your machine. Pass the same graph options you generate with (`--plugin`, `--scip-index`, `--ambiguity-ceiling`, `--secret-prefix`, `--corpus`).

The answers go to `model-verification.json` in the corpus directory. Each answer is also cached in `.ra-verify-cache/` under a hash of the whole question, so a second run sends nothing for sites that have not changed, and a run that stops halfway continues where it stopped. Generation reads the file only with `--model-verification`. With that flag, a "maybe also" line the model answered gets a "model-verified" mark: the candidate the model named moves to the front, or the line says the model named none of them. Nothing is removed, the manifest does not change, and a site an index judged ignores the model. `coverage.json` counts the answers that were used, the stale ones (the code or a candidate changed since) and the ones whose site is gone.

### Optional: let a model say what a type is for

Where the purpose read from the code is thin, `reverse-architect verify <repo> --purpose --backend ollama|openai-compat|claude-cli` asks a model for one sentence per type. The model sees the facts the type's card and detail hold — its name, kind and signature, the purpose sentences read from the code, its bases, the types it uses and is used by, its database accesses and its anchors — and no source code. Every field passes through the secret filter with your `--secret-prefix` values first, and a text the filter withheld is never sent. `--lang en|cs` chooses the language of the sentences, and `--dry-run` prints how many types would be sent and roughly how many tokens that is. An answer must be one line of at most 400 bytes and may name no number, identifier or code span the facts do not contain. Any other answer is counted as invalid and asked again next time.

The sentences go to `model-purpose.json` in the corpus directory, cached in `.ra-verify-cache/` under a hash of the facts, the prompt version, the backend and the language. Generation reads the file only with `--model-purpose`, and then shows a sentence as its own line at the end of the card's `## Purpose`, labelled `(written by a model, not read from the code)`. The header, the map row and the manifest keep the purpose read from the code. A sentence whose type's facts changed since, or that was asked in another language, is not shown, and `coverage.json` counts the sentences used, stale and unmatched. Without the option, the corpus is byte for byte what it is without the file.

## Plugins

A language plugin is a WebAssembly component built against the contract in [`wit-v2/extractor.wit`](wit-v2/extractor.wit) (`ra:plugin@0.2.0`). The previous contract, [`wit/extractor.wit`](wit/extractor.wit) (`0.1.0`), is frozen and still loaded, so a plugin built against it keeps working. A plugin sees one file at a time. It returns what the file declares and which names the file uses, and under 0.2 also what the syntax says around each use. The host resolves those names across the whole repository with one shared set of rules. Every plugin therefore gets the same handling of ambiguous names, and no plugin can claim a relation the core would call a guess.

```sh
reverse-architect path/to/project --plugin my-lang.wasm
reverse-architect path/to/project --plugin my-lang.wasm=sha256:9f86d0…   # refuse any other bytes
```

- **Order is precedence.** A declared plugin takes the extensions it claims ahead of the bundled ones. A declared plugin whose id matches a bundled one (`csharp`, `rust`, …) replaces it.
- **The sandbox grants nothing.** A plugin gets no files, no network, no environment and a frozen clock. Fuel and memory are capped, so a plugin cannot hang or exhaust the host. A file a plugin fails on is reported in `coverage.json` with the reason, and the run carries on.
- **The corpus says what built it.** The manifest lists every plugin with its version and SHA-256, and every fact names the plugin that produced it.

[`examples/plugin-sql`](examples/plugin-sql) is a complete plugin in about 600 lines of Rust. It is built outside this repository's build graph, against the 0.1 WIT alone, and it is also the bundled SQL plugin. [`examples/plugin-xaml`](examples/plugin-xaml) is a second one, on contract 0.3, and the bundled XAML plugin. Start there. [docs/plugins.md](docs/plugins.md) describes both contract versions.

## Format versions

Consumers that read the corpus should check its version fields. The three levels changed these formats:

| File | Version field | Now | Before | What changed |
|---|---|---|---|---|
| `manifest*.json(l)` | `schema_version` | 10 (11 when the corpus declares kinds of its own) | 9 (10) | Two document kinds: `map` (id `map:<module>`) and `card:detail` (id `detail:<card identity>`). Four optional fields on the map, card and detail documents: `level` (`map`, `card`, `detail`), `parent`, `embed` (`false` on every detail) and `header` (`path`, `module`, `namespace`, `kind`, `name`, `purpose`). A node's facts may carry the kind `db_access`, text `<access> <object>` with `reads`, `writes`, `calls` or `mentions`. The graph's other new fact kinds (`anchor`, `anchor_skipped`, `anchors_dropped`, `enum_decision`, `enum_decisions_unmatched`) never reach the manifest: the detail and `coverage.json` are their only projections. A SQL statement in a C# raw or interpolated literal now yields its `uses` edges and `db_access` facts. A corpus built with `--detail-level` names the level in `detail_level` and lists the body component in `plugins`, with no version bump. |
| `coverage.json` | `schema_version` | 6 (7 when the corpus declares node kinds) | 5 (6) | C and C++ files are named as languages, with the reason that no plugin reads their declarations. New sections: `enum_decisions` (the places C# decides by an enum, by what the host could make of them), `anchors` (kept, dropped by the cap, withheld by reason), `db_accesses` (by state), `cards` (the type cards with no comment sentence in their purpose, the details written, left out and cut into parts, the maps and their parts, and the median and p90 size in bytes of a map row, a type card and a detail), and `model_purpose` with `--model-purpose`. With `--detail-level`, a `bodies` section: the level, the plugins that read bodies, how the bodies paired with the declarations, what paired with nothing, and every file the pass failed on. |
| cards | `schema` in the front matter | 6 | 5 | The type card is the short card, and its lists, the API, the diagram, "Maybe also" and the quoted comment moved to the detail (`kind: detail`). Cards gained `## Purpose` with the origin of each sentence and `## Keywords`. A module card links its map (`kind: map`), and a file card links its file detail when it has one. |
| type cards of a `--detail-level` run | `schema` in the front matter | 7 | 6 | The front matter adds `detail_level: N` and `layer2: present\|failed\|none`. With `present`, `## Purpose` reads the purpose from the code with the doc comment as a quote, and `## Functionality: …` and `## State: …` sections follow `## Keywords`. A card with `failed` or `none` is otherwise the card of a run without the layer. Every other card, every detail and every map of such a run stays at 6, so one corpus holds both. |

The two numbers in the manifest and coverage rows do not have to rise together: a manifest at 11 beside coverage at 6 means the corpus declared kinds, none of them node kinds. The cache format changed too, so the first run after an upgrade parses everything again. A consumer that imported cards of format 5 should replace every imported document rather than update them one by one. New files appear only when asked for: `sites.jsonl` with `--sites`, `model-verification.json` written by `verify`, `model-purpose.json` written by `verify --purpose`, and `index.scip` with `index.record.json` written by `index`.

The previous release changed the formats for the confidence levels: manifest 9 brought `confidence`, `rule_id` and `sites` on name-resolved edges, coverage 5 the `noise` section and `languages[].contracts`, and cards 5 the `## Maybe also` section and one row per relation listing all its sites.

## Guarantees

- **Deterministic.** Same input, same bytes, down to the order of every list.
- **Offline.** Generation fetches nothing and sends nothing. Only the optional steps reach out, and only when you run them: `enrich` and `verify` talk to the model backend you name, and `index --restore` downloads packages.
- **Sourced.** Every claim carries a file and line, and every relation found by name carries its confidence level.
- **Honest about gaps.** `coverage.json` names every file nothing could read and says why. A missing edge is never presented as an absent relationship.
- **Redacted.** String literals and comments that look like credentials are replaced before they reach any output: the anchors, the keywords, the purpose, the manifest, the cache and what `verify` sends to a model included. A literal is judged together with the code on its line (`password = "…"`, `heslo = "…"`), a comment as one block, and a long token with no spaces and mixed characters is never an anchor or a keyword. A withheld text leaves its place and the reason. A message that only names a password, such as `Chybné heslo`, stays searchable. `--secret-prefix` adds your own token shapes.

## Measuring search

[`tools/search-eval`](tools/search-eval/README.md) is a separate Python runner that measures whether an agent that also reads a reverse-architect corpus as plain files finds the cause of solved support cases more reliably and more cheaply than an agent with the sources alone. It can also compare two corpora built with different options. It stays outside the binary. Its procedure is documented in Czech.

## Building from source

```sh
cargo test                     # host and bundled plugins
cargo run -- path/to/project
```

The bundled plugins are committed prebuilt under `plugins/prebuilt/`, so building the tool needs no WebAssembly toolchain. Rebuilding them does: see `plugins/build.sh` (wasi-sdk 34 for the tree-sitter grammars, which are C).
